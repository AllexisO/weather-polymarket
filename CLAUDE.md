Поиск честного преимущества (edge) на погодных маркетах Polymarket (47 городов, «Highest temperature»).
Оператор и единственный разработчик — Alex. **Реальных денег нет** — только виртуальные кошельки
(`/paper`). Проект `polymarket-markets` (всё, кроме погоды) удалён 09.10 по решению Alex — толку не было.
Главная модель — v5 «от рынка», кошелёк **`ml5`** (с 20.10, решение Alex; до этого v3 / `ml3`).

**Подробности — открывать только когда нужно для задачи:**

- `docs/AUDIT.md` — полная проверка проекта: как проверять, что находили раньше (смотреть перед следующей проверкой);
- `docs/DESIGN_SYSTEM.md` — цвета, компоненты, правила страниц (смотреть перед правкой шаблонов);
- `docs/CLAUDE_archive_*.md` — история решений и цифры.

## ОБЯЗАТЕЛЬНО до первой ставки нового кошелька / источника / правила (решение Alex 12.10)

`./check.sh` проверяет, что код работает, а не что он считает как Polymarket. Поэтому до запуска:
1. **Правила маркета** — прочитать описание маркета города (Polymarket, поле description): станция, источник итога,
   точность и округление (целые / десятые, отбрасывание или округление), где граница дня (полночь по местному), °F/°C.
2. **Прогон на прошлом против настоящих итогов** (`weather_poly_outcomes`) — все дни, где есть данные (минимум 7):
   правило кошелька на каждом дне должно давать то же, что итог Polymarket (источник замеров: максимум дня по правилам
   кошелька не «убивает» выигравший вариант ни разу). Хоть один день расходится — не запускать, найти причину.
3. Итог проверки (дней, расхождений) — в комментарий у правила и в `app/wallet_docs.py`.
Уроки 11-12.10: Гонконг (полночь, отбрасывание десятых), США (целые °C → °F), KNMI (другое усреднение) — все три
были видны до первой ставки.

## Путь кошелька до Live (договорились 04.11)

Каждая идея проходит 4 шага; пропускать нельзя. Переходы 1→2 и 2→3: Claude считает в дату порога и пишет итог числами,
подтверждает Alex; 3→4 — только прямое решение Alex.
0. **До первой ставки:** карточка в `wallet_docs.py` (от какого кошелька, что одно меняем, зачем); правила маркета и прогон
   на всей истории итогов (с 01.06.2025, где есть данные кошелька; минимум 7 дней — раздел выше); **порог шага 1 — заметкой до первой ставки**: ≥ N закрытых (N — сколько кошелёк сделает за 2-4 недели,
   не меньше 40), ≥ 14 дней, доходность ≥ +5% с комиссией, шанс получить её удачей ≤ 5%; вариант другого кошелька — ещё и
   больше «родителя» в $ на тех же днях.
1. **Кошельки** (/paper, $100, ставка $2). В дату: прошёл → предложить шаг 2; не прошёл → выключить или оставить в Кошельках;
   мало ставок → продлить, порог не снижать. До слова «прошёл» — проверка данных и логики (deep_check), «слишком хорошо» → искать ошибку.
2. **Симуляция** (/real): кошелёк на **своей части** настоящего счёта (см. ниже) с пределами риска и покупкой по стакану в момент
   решения (decision_books). Сначала прогон ставок шага 1 (повторяет ≥ 95% настоящих ставок, иначе искать причину), затем 14 дней
   вперёд. Порог: в плюсе на своей части, доходность ниже бумажной не больше чем на 3 п.п., ни разу не упёрся в свою часть и пределы.
3. **Вхолостую** (`real_exec`): 14 дней, каждая ставка → подписанная заявка, не отправляется; порог — 0 расхождений (цена и размер
   со стаканом в эту секунду, учёт `weather_fast_dry.py --report`, остановка биржи → не ставим).
4. **Live:** один настоящий счёт $100, рядом бумажный двойник; ежедневная сверка, отставание от двойника > $10 → стоп и искать причину.

**Один счёт, кошельки не мешают друг другу (во 2, 3 и 4 шаге):** у каждого кошелька своя часть счёта (учёт у нас, на бирже счёт один);
ставит только из неё, выигрыш и проигрыш остаются в ней. **Размер части = максимум в ставках одновременно + худшая просадка** на его
ставках шагов 1-2, вверх до $5 (04.11 по ставкам 24.10-04.11: fav ~$20, ml4e_cal ~$30, ml5_cal ~$35, ml_day ~$45, ml5 ~$50).
Это нижняя граница части. На старте подключаются только кошельки, чьи части помещаются в $100; как делить остаток $100
(больше каждому или держать для следующих) — решаем при запуске Live, по тому, сколько кошельков прошли. Новый кошелёк (прошёл шаг 3) получает часть **из прибыли**:
поровну вычитается из частей остальных, но только сверх их нужного размера; не хватает — ждёт. Один вариант у двух кошельков —
одна заявка, доли делятся по средней цене, разница с покупкой «в одиночку» видна отдельно. На странице Live — строка на кошелёк
(в ставках, ставок / выиграно, заработал, пропущено), сверху счёт: было, сейчас, свободно.
Общий банк 5 кошельков (`fav`, `ml5_cal`, `ml5`, `ml4e_cal`, `ml_day`) не трогаем — его решение 21.11 (#113, `docs/PRD.md` §4а).

## ОБЯЗАТЕЛЬНО после любого изменения кода

**`./check.sh` — не заканчивать, пока не «ПРОВЕРКА ПРОЙДЕНА»** (сборка, колонки, прогон всех
кошельков в памяти, все страницы). Новая модель/кошелёк: сначала колонка (ensure_schema), потом
кошелёк. Меняешь правило кошелька — поправь `app/wallet_docs.py`. Меняешь устройство — поправь `docs/`.
**Одна ошибка не роняет весь запуск:** цикл по городам / трейдерам / дням оборачивать в
`with item_guard(city, conn):` (`jobmark.py`) — элемент пропускается и догружается в следующий раз,
остальные идут дальше; пропуски видны на /status как «с пропусками».
**Починил ошибку скрипта — сразу отметь:** `docker compose run --rm --entrypoint python collector fixes.py <скрипт> "что исправлено"`
(`--at` — если исправлено раньше). Иначе старые падения висят как проблема. Ошибки Alex — по-человечески:
название скрипта из `jobs_info.py`, сколько раз, когда последний раз — не «weather_copy ×2».
**Проверки в течение дня** — `night_check.sh morning` (07:00, «ночь прошла?»), `midday` (13:00, «утренние решения приняты?»), `evening` (23:30, «ночь пройдёт?»); результат вверху /audit вкладками.
**Отложенное на дату** (проверить порог, решение по кошельку) — сразу в заметки: `docker compose run --rm --entrypoint python collector notes.py add ГГГГ-ММ-ДД "что" "подробности" --time ЧЧ:ММ` (время по Кишинёву; по умолчанию 10:00 — ночные задачи уже отработали; нужны данные текущего дня — позже, например 21:00) (страница /notes, утренняя проверка напоминает).

## База

- SQLite `data/db/polymarket_lab.sqlite3` (~6 ГБ, WAL). Скрипты: `docker compose run --rm collector <скрипт>`.
- **Исследования — только на копии**: `docker compose run --rm -e JOB_TIMEOUT=0 -e POLY_LAB_DB=/data/research/research.sqlite3 collector ...`
  — долгие запросы к рабочей базе блокируют крон («database is locked»).
- Предел времени запуска — `JOB_TIMEOUT` (по умолчанию 40 мин); сторож `db_watchdog.sh`.
  В постоянно работающих процессах — короткие соединения и `rollback()` при ошибке.
- Open-Meteo: ~10 тыс. вызовов/сутки, крон тратит 5-6 тыс. — большие загрузки делить.

## Методология

1. Порог решения фиксируется числом ДО просмотра результата.
2. Подбор на одном периоде, проверка на другом; деньги — по настоящим сделкам (`poly_trades`), с комиссией.
3. Варианты модели сравнивать по среднему нескольких обучений (разброс ±0.015).
