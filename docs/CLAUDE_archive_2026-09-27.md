# polymarket-lab

Поиск честного преимущества (edge) на Polymarket. Отдельный проект, НЕ
gold-sim (там — копи-трейдинг на демо Capital.com). Оператор и
единственный разработчик — Alex. **Реальных денег нет** — только
виртуальные (paper) кошельки. Полная история решений до 2026-09-25 —
`docs/CLAUDE_archive_2026-09-25.md` (там подробности и цифры).

## Как работать с Alex

- Коротко, простым языком, без жаргона. Отвечать по-русски.
- Результат показывать **в долларах через виртуальные кошельки** (`/paper`),
  а не в процентах попаданий.
- Любую новую идею — **отдельным кошельком/вариантом**, не менять две
  вещи сразу, иначе не понять, что сработало.
- Не предлагать «подождать ещё данных» или «закрыть направление» —
  искать конкретные методы. Решения о городах, ставках, платных API —
  за Alex.
- Про ML: Alex уверен, что обучение на данных работает — не говорить
  «нельзя», а объяснять, как сделать лучше.
- **Слишком хороший результат — сначала искать ошибку**, потом
  показывать (урок: +$7260, оказавшиеся протухшими ценами).
- Во внешние API не передавать личные данные (email в заголовках и т.п.).
- Реальные деньги — только по прямому решению Alex. До этого нужно:
  код реальных заявок (py-clob-client) прогнать вхолостую, пополнение/
  вывод USDC, проверить доступность Polymarket в стране Alex, заранее
  записанный порог перехода (напр., ≥150 закрытых ставок главной модели).

## ОБЯЗАТЕЛЬНО после любого изменения кода

**`./check.sh` — и не заканчивать, пока не «ПРОВЕРКА ПРОЙДЕНА».** (правило Alex, 2026-09-27,
после падения всех кошельков из-за колонки ml4, которой ещё не было в snapshots.)
Проверяет: сборку всех скриптов, что у каждого кошелька есть его колонка, что снимки пишут
только существующие колонки, **прогон всех кошельков в памяти** (решения по-настоящему,
покупка подменена, рабочая база не меняется), загрузку модулей и все страницы дашборда.
Новая колонка / модель / кошелёк: сначала создать колонку (ensure_schema), потом включать
кошелёк. Та же проверка (`preflight.py`) идёт каждые 30 мин в weather_alerts.py — при
ошибке красная плашка на /paper.

## Инфраструктура

- TrueNAS, `/mnt/applications/docker/stacks/polymarket-lab`. Скрипты —
  одноразовые запуски по крону: `docker compose run --rm collector <скрипт>`.
  Дашборд — отдельный контейнер `dashboard`, порт 8093.
  Слушатель сделок `copier` (weather_copy_live.py, websocket ws-live-data.polymarket.com,
  все сделки Polymarket за 0-1 с с кошельком трейдера) — постоянно работающий контейнер,
  `docker compose up -d copier`; повтор за сильными трейдерами за секунды.
- SQLite `data/db/polymarket_lab.sqlite3` (~4.4 ГБ на 2026-09-25).
  **Резервных копий нет** (ни git — так задумано, ни ZFS-снимков) — предложено
  Alex, не сделано.
- Образ collector: requests, numpy, pandas, lightgbm (+libgomp1).
- LLM: Ollama `qwen3:8b` в домашней сети (адрес — `OLLAMA_URL` в `.env`) (~4 с на запрос).
- Open-Meteo (бесплатно, ~10 тыс. вызовов/день, 600/мин; ансамбль весит
  ~1 вызов на 10 членов) — на 48 городах лимит близко, поэтому паузы и
  WeatherNext 2 только на 6 городах.
- Ключи (`.env`, не в git): the-odds-api, OddsPapi.
- Git: только локальный, коммиты по просьбе.

## Погода — главное направление

### Основа

- **48 городов** (`app/weather_cities.py`: ICAO, часовой пояс, °F/°C,
  координаты станций) — все маркеты «Highest temperature in X», которые
  Polymarket резолвит по METAR через NOAA (кроме Гонконга, Тайбэя, Цзинаня).
- **Факт** — `weather_station_daily` (METAR из Iowa Mesonet), совпадает
  с исходом Polymarket в 97-100%. Официальный исход — `weather_poly_outcomes`.
  Старый «факт» из Open-Meteo (`weather_outcomes`) был неверным — не
  использовать. Polymarket считает **только METAR**, 5-минутные замеры
  США НЕ засчитываются.
- **Комиссия на погоде есть**: доли × 0.05 × p × (1−p), только с того, кто
  забирает заявку; минимум 5 долей, шаг цены 0.001.
- **Рынок очень точен**: цена ≈ реальная частота во всех ценовых
  корзинах; переплаты за «лотерейные билеты» нет.

### Проверено и НЕ сработало (не повторять без новой идеи)

- **Гонка за замерами**: рынок убирает цену на мёртвый вариант через 0-3
  мин после замера, мы видим METAR через 2-6 мин (оба источника: awc,
  tgftp). Денвер (KBKF) — METAR опаздывает на ~25 мин. Платные быстрые
  данные (wethr.net $15-99/мес, Synoptic HF-ASOS, только США) дали бы
  паритет, не преимущество.
- **Бэктест на `price_history`** — это цены последних СДЕЛОК с точкой каждые
  5 мин даже без торгов: «свежесть» по нему не проверить. Реалистично —
  только `poly_trades` (все сделки за 30 дней).
- Правила ставок для микса (48 вариантов), ставки против «лотерейных
  билетов», nowcast по замерам в течение дня — всё в минусе на проверке.
- Маркет-мейкинг: выставляющий заявки в среднем теряет ~0.6%.
- Поправки по ветру/облачности, соседние станции, разборы метеорологов
  через LLM — точность не растёт. Claude читает разборы точнее Qwen
  (1.77 против 2.54°F), но всё равно хуже микса моделей (1.43°F) —
  Claude API не заводим (решение Alex).
- WeatherNext 2 — занижает на ~2° (похоже, 6-часовой шаг).
- **Исследования 2026-09-26** (`weather_study_0926.py`, `weather_study_hour.py`;
  подбор июль-авг, проверка сентябрь, деньги по реальным сделкам `poly_trades`):

## Другие направления (кратко)

Общий урок: **edge заметно больше обычного — сначала подозревать баг**
(сопоставление команд, неправильный эталон, подглядывание в будущее).

- **Спорт** (`sports_edge.py`, `sports_resolve.py`): Pinnacle (the-odds-api,
  бюджет 500 запросов/мес, крон раз в день) против Polymarket; **26.09: лимит the-odds-api исчерпан (500/500),
  данные спорта не собираются с 22.09 до сброса лимита в начале месяца;** с 26.09 сбор и
  итоги — раз в 2 дня (~400 запросов/мес вместо ~1300), лиги не в сезоне пропускаются, при
  остатке < 20 скрипты больше не запрашивают (`RESERVE` в sports_edge.py); 5 футбольных
  лиг + NFL/NCAAF/NBA/WNBA. Наравне с рынком (~51% против 51%). Баги были:
  матч уже шёл; сопоставление команд (стоп-слова вроде «sc», «Utah» vs
  «Utah State» — теперь полное покрытие токенов).
- **Новости о составе** (`sports_news.py`): Google News → Qwen3 → сигнал
  отсутствие/возвращение игрока; совпадает с рынком, опережения нет.
- **Киберспорт** (`esports_edge.py`, `esports_resolve.py`): Pinnacle через
  OddsPapi (250 запросов/мес, ошибки тоже списываются; пауза 2 с,
  ≤6 платных запросов за прогон, раз в 2 дня); резолв через Polymarket.
- **Арбитраж с Kalshi** (`kalshi_edge.py`): расхождения 0.5-1.5%, резолвера нет.
- **Макро** (`macro_edge.py`/`macro_resolve.py`): CPI (NSA-ряд!), безработица,
  JOLTS, ВВП (GDPNow) на FRED; наивная модель заметно шире рынка.
- **Твиты Маска** (`musk_tweets_*`): xtracker.polymarket.com; фильтр дат по ET
  проверять самим.
- **Закрыто**: всё, что резолвится по цене актива (крипта 5-мин, золото,
  индексы, форекс, ставка ФРС) — эталон = та же цена, круговая зависимость.
- Дашборд: `/status` (вердикт с порогами `VERDICT_MIN_N=30`,
  `VERDICT_MIN_GAP=5 п.п.`), `/calibration`, вкладки по направлениям.
  Калибровка берёт **один снимок на день/матч** (был баг задвоенного n).

## Методология (из gold-sim)

1. Диагностика частоты раньше PnL.
2. Kill criterion фиксируется числом ДО просмотра результата.
3. Выборка и walk-forward, не единичные примеры; подбор — на одном
   периоде, проверка — на другом.
4. Всегда учитывать спред и комиссию (на погоде комиссия есть — см. выше).
5. Реальные деньги — только после честного paper-лога, по решению Alex.
